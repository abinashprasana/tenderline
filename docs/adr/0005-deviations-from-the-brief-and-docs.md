# ADR 0005: Where reality differed from the brief or from memory

**Status:** accepted. Each point was checked against the live service or the installed package.

- **TED query syntax.** `SORT BY publication-date ASC` is a syntax error; ascending is the default, descending is `SORT BY publication-date DESC`. Dates use `publication-date>=YYYYMMDD`; CPV wildcards use `classification-cpv=72*`. The brief says "scroll token"; the API names it `paginationMode: "ITERATION"` with `iterationNextToken`, max 250 notices per page.
- **TED fair use.** Documented limit is 700 requests per minute. A burst of ~12 rapid requests from one IP still returned HTTP 429, so the client paces itself (default 60/min, refuses configuration above 600/min), honours `Retry-After` and backs off exponentially with full jitter.
- **Field shapes** (recorded in `tests/fixtures/ted`): buyer name `{"eng": ["..."]}`, lot values as string lists with a parallel currency list, duplicated CPV codes, date-only deadlines like `2026-12-16Z` (stored as end of that day in UTC with `deadline_precision="date"`). Corrigenda: notices are versioned when the same publication number changes content, or when a new publication number shares the same `notice-identifier`. **Not verified:** how TED publishes corrigenda for each notice type.
- **Awards** link to calls through `procedure-identifier`, shared by both notices.
- **eTenders CSV** is Windows-1252, dates are `DD/MM/YYYY`, additional CPV codes are `;`-separated. Columns are detected from the header; the file is imported from a path and never downloaded by the app.
- **SQLAlchemy is pinned below 2.1**: OpenTelemetry's SQLAlchemy instrumentation does not support 2.1, and we want database spans in traces.
- **DBOS**: see ADR 0001 for the event-loop, `send` and executor-id findings.
- **Histogram buckets.** The OpenTelemetry SDK default buckets assume milliseconds, which made a 24 ms p95 read as ~4.7 s in seconds-based metrics; explicit bucket boundaries are set for HTTP and LLM latency.
- **Database defaults** for status/counter columns live in the database (migration 0004), not only in the ORM.
- **Saved-search backfill is capped.** Creating a saved search matches it against stored open notices (not in the brief, but a new search must show today's opportunities). A k6 write test that created hundreds of searches once queued ~43,000 qualification workflows and starved the queues, so a backfill now auto-qualifies at most `BACKFILL_QUALIFY_LIMIT` (default 50, newest first); the remaining matches stay visible and can be qualified on demand with `POST /v1/organisations/{id}/matches/{match_id}/qualify`.
- **Parsing and normalisation happen at ingestion, not on the enrichment queue.** The brief lists "parse, normalise buyers and CPV codes, match" as one queue stage. We parse, normalise buyers and CPV codes and store each version inside the same transaction that advances the ingestion cursor, so a crash can never advance the cursor past unstored data and re-running a page is idempotent (content hash). The enrichment queue (concurrency-limited) then handles routing (award, corrigendum, new call) and matching, which is the part that fans out across organisations.
- **TED corrections are separate notices.** Checked against live data: a change notice has its own publication number and its own `notice-identifier`, and names the notice it corrects in `change-notice-version-identifier` as `<identifier>-<version>`. A chain of corrections points at the previous correction. We store a change notice as a new version of the notice it corrects, and ignore an original that arrives after its correction. The earlier assumption (same identifier, new publication number) was wrong and produced duplicate notices.
- **A timed-out TED search returns HTTP 200** with `timedOut: true`. The client treats it as a failed page and retries.
- **Tracing fan-out.** One request that queues many jobs now starts a separate, linked trace per job, as the OpenTelemetry messaging conventions recommend. A saved-search backfill had produced single traces with up to 9,475 spans.
- **Not done:** provider-side structured output (JSON schema mode) for Groq and Gemini. It depends on the model and could not be tested without keys, so the server-side validation remains the only guarantee. The production backup container still installs the AWS CLI at start-up when uploads are configured.
